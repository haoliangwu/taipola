# taipola

一个极简但强大的 Markdown 编辑器：**光标所在的那一行显示 Markdown 源码，光标一离开就渲染成最终的样子**。没有左右分栏，没有预览按钮。

```bash
pnpm install
pnpm dev      # http://localhost:5178
pnpm build    # 产出 dist/
```

## 现在能做什么

- 即时渲染：段落、标题、列表、引用、代码块（highlight.js 高亮）、表格、任务列表、脚注
- 中文输入法原生可用（拼音候选、联想词不受干扰）
- 原生撤销栈：`Cmd/Ctrl + Z` 由浏览器提供，快且跨命令可靠
- 打开 / 保存 md 文件；浏览器支持时写回**原文件**（File System Access API），否则降级为下载
- 侧边大纲：随光标高亮所在章节，点击跳转
- 自动保存草稿到 localStorage，关页面不丢内容
- 导出 HTML / 导出 MD
- 主题：默认跟随系统，右上角可切换 **浅色 → 深色 → 跟随系统**（选择会被记住）

快捷键：`Cmd/Ctrl + B/I/K/E`（粗体/斜体/链接/行内代码）、`Cmd/Ctrl + 1..6`（标题级别，重复按同级别可取消）、`Cmd/Ctrl + Shift + K`（删除整行）、`Cmd/Ctrl + O/S`（打开/保存）、`Cmd/Ctrl + Shift + S`（另存为）、`Cmd/Ctrl + Shift + \`（切换大纲）。

### 主题

`:root` 携带浅色配色（默认，纯白底）。深色有两条触发路径，都写在 `src/styles.css`：

- **系统偏好**：`@media (prefers-color-scheme: dark) :root:not([data-theme='light'])`
- **显式选择**：`:root[data-theme='dark']`，写在最后，因此总是优先于系统偏好

`useTheme()`（`src/lib/theme.ts`）负责把选择写到 `<html data-theme>` 并存进 localStorage。`system` 时移除该属性，交还给媒体查询。

配色全部走 CSS 变量，所以**切换主题不影响行高与布局**（行盒高度是固定值，不随主题变化）。代码高亮的 token 颜色在深色下单独重新着色——highlight.js 只提供浅色主题，深色下若不覆盖会对比度不足。

## 架构：单容器 + 逐行渲染

```
.doc                        唯一的滚动容器
└── .blk                    一个块，高度 = 源码行数 × 行高（固定）
    └── .ln                 一行源码 = 恰好一个行盒
```

**光标就在渲染出来的文字里。** 光标所在的块切成 `contenteditable` 并显示原始 Markdown，其余块渲染成样式。因为渲染行和它的源码行是**同一个元素**，对齐由构造保证 —— 不存在"同步两个滚动容器"这回事。

### 为什么不是"透明 textarea 叠在渲染层上"

第一版就是这么做的，那是**结构性缺陷**，不是精度问题：

`textarea` 的高度恒等于 `行数 × 行高`，而渲染层的高度由内容决定。两者天生不等（实测一份 59 行的文档差 **350px**）。只要不等，"同步滚动"在任何意义上都无法精确 —— 差值会**逐块累加**，越往下偏得越狠。

我在这条路上修过三轮（锚定最上方块、归一化滚动范围、增量 padding 恢复），把误差压到了 0.3px，但那是**在两个不可调和的东西之间做映射**。根本矛盾是：

> "源码行数决定高度" 与 "每块渲染成多行样式化内容" 无法同时成立。

实测数据很直接：一个渲染块**必然**比它的源码行占更多行。`## 行内样式` 是 1 行源码、3 行渲染；列表渲染 394px 而源码只有 6 行。要让两层等高，只能把内容缩放到 **0.33** —— 15 个块里 14 个需要缩放，9 个严重变形。**此路不通。**

现代编辑器（Typora、Obsidian Live Preview）的做法都是**不要两个容器**。taipola 现在也是。

### 支撑这套设计的核心不变量

**一行源码 = 恰好一个行盒**（`--doc-line`，26.25px）。

因此一个块的高度精确等于它的源码行数，下方任何内容都不会被推移。这条不变量由 `src/lib/inline.ts` 保障：

- 块级语法（列表符号、引用 `>`、围栏 ```、标题 `#`）从行首**剥掉**，改用样式表达（`aria` 之外的伪元素、缩进、字重），因为任何带 margin/padding 的包裹元素都会让渲染行变高
- 标题只改 `font-size` 和字重，**行高固定不变**
- 列表标记、任务框、引用竖线都是 `display: inline-block; height: 1em` 的行内元素
- 渲染块用 `overflow: hidden` + 固定高度（`行数 × 行高`）

调试时可以读 `window.__taipola`（仅 dev 构建）看行盒数与不变量。

### 三个会破坏光标的坑（都踩过）

1. **`focus()` 会重置选区。** 必须先 `focus()` 再 `setRange()`。反过来写会静默丢弃刚设好的光标，之后每次击键都插到行首 —— 表现为输入**逆序**（打 `ABC` 得到 `CBA`）。
2. **React 重渲染会重置 `contenteditable` 内的选区。** `setDoc` 更新模型后，浏览器把选区扔回偏移 0。所以每次输入后都要把光标位置存进 `pendingCaret`，在 layout effect 里重新应用。
3. **点击必须显式定位光标。** 块已经是可编辑态时若只 `preventDefault()` 而不自己算位置，光标会停在原处。定位用二分查找测量每个字符的宽度中点，把点击的 x 换算成字符下标；渲染态还要再经 `visibleToSourceIndex` 跳过 `**`、`[]()` 这些标记。

### 撤销

`contenteditable` 的原生撤销栈跨块不可靠（块会挂载/卸载），所以用**自己的快照栈**：每次结构性修改前压入 `{value, caret}`，`Cmd/Ctrl+Z` / `Cmd/Ctrl+Shift+Z` 在栈间移动，恢复时连光标一起还原。

## 已知限制

- **表格按行渲染，不是真正的表格盒子**：每行保持一个行盒（这是对齐的前提），所以没有列对齐和边框，分隔行 `| --- |` 不可见。真正的表格需要放弃该行的"一源码行 = 一行盒"约束。
- **块内不做换行重排**：渲染态每行按源码行显示，长段落在渲染态不会自动折行。这是"一行源码 = 一行盒"的直接代价，也是对齐成立的原因。
- 图片会按行内元素渲染，高度受限于一个行盒；加载完成后不会引起位移。
- mermaid、数学公式尚未支持。
- 单文档全量重解析，超大文件（数万行）会有输入延迟。
