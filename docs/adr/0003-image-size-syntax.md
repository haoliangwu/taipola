# ADR-0003: 图片尺寸用 `{width=…}` 后缀，只收像素

- 状态：**已执行**（2026-09-12）。语法定了；拖拽手柄那类 UI 不在这次范围内。
- 关联：`.scratch/image-resize/issues/01-images-cannot-be-scaled.md`（原始缺口与三条候选）。
- 关联：`docs/adr/0002` 的 run 分段约定——这次动的是图片 run 的边界，光标进到后缀里时整段让位给源码。

## 1. 问题

Markdown 没有指定图片尺寸的写法，屏幕上那张图多大完全由文件本身决定。同一张图要在文档里出现两种
大小，只能存两份文件。欢迎文档开头那个头像就是这么来的：`docs/logo.webp` 生成时就缩到 128×128，
不缩就会占满整个文档列宽。

## 2. 决定

在图片后面紧跟一个后缀，读作像素宽度：

```markdown
![alt](url){width=200}
```

- **只收整数像素**（`{width=200}`）。不收百分比，也不收 `px` 单位：百分比得落到 `style.width` 上，
  而导出的净化配置禁掉了 `style`（`platform/html.ts` 的 `FORBID_ATTR`），两边立刻分岔；
  像素写法在屏幕上和导出里都是同一个 `width` 属性，没有换算，也没有第二套表示。
- **后缀属于图片**。`![alt](url){width=200}` 在源码里整个是一个 run，屏幕上是同一张 `<img>`，
  元素上的隐藏副本仍带着完整源码，所以从 DOM 重建文档不会丢后缀。光标落在后缀里时，图片照旧让位给源码。
- **一份读取器，两个调用方**。`core/imageSize.ts` 的 `readImageSize` 同时被屏幕侧（`core/view.ts`
  的扫描）和导出侧（`core/markdownIt.ts` 里的一条 core 规则）使用。上一条「同一套语法两处实现」的
  代价记在 `.scratch/autolinks/issues/02`，这次不重演。

没有采用的两条路：

- **打开作者的内联 HTML**（`<img src width>`）。`html: false` 是一条安全决定，不是默认值：
  这是编辑器，不是浏览器。为图片尺寸开一个标签的白名单，等于把这条决定降级成「白名单够不够全」的
  持续判断，而收益只是一条语法糖。
- **只做拖拽手柄，不改语法**。手柄最终也要把尺寸落到源码的某个地方，那还是这条决定；先不定语法，
  手柄就没有可依赖的表示。所以语法先行，UI 之后再说。

## 3. 代价

- **这份文件在别的编辑器里会多出一段正文**。它们只把 `{width=200}` 当文本显示。这是选 B 而不是 A 的
  代价：换来的是一句话能说清的安全模型，付出的是文件里有一段非标准语法。
- **语法是窄的**。`{width=200}` 必须紧跟在 `)` 后面，中间有空格就当正文；`{width=20%}`、`{width=200px}`
  同理。窄是有意的：将来要放宽（百分比、高度），两边读的是同一个 `readImageSize`，改一处就够。
- **图片 URL 里带括号时两边不一致**（`![a](x(1).png)`）。屏幕侧的行内扫描是手写的，`[^)]*` 停在第一个
  `)`，导出侧按 markdown-it 解析。这是**既有**偏差，与尺寸后缀无关；实测记在
  `.scratch/image-resize/issues/01-images-cannot-be-scaled.md` 的 Comments 里。
- **引用式图片**（`![a][ref]`）屏幕侧不渲染（既有），导出侧会正常吃掉后缀。同样记在那张票里。

## 4. 留下的东西

- `src/core/imageSize.test.ts` —— 语法本身的边界：认哪些写法，不认哪些。
- `src/platform/html.test.ts` —— 同一份源码分别问屏幕和导出，答案必须一致；以及「同一张图两种尺寸，
  只存一份文件」。
- `src/shell/components/Editor.test.tsx` —— DOM 里真的是 `<img width="200">`，`assertDomMatchesSource` 仍然过。
- `docs/logo.webp` 保留。它 128px 对头像本来就是合适的尺寸（12KB，原始 `logo.png` 是 687KB），
  不是因为不能缩放才存在。
